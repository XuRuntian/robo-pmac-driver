## 邮箱问题与修复范围

固定 IgH 源码 `master/globals.h` 定义 `EC_WAIT_SDO_DICT=3`。`fsm_master.c` 在 PREOP 等待后自动读取对象字典，`fsm_slave.c` 同时可处理 CLI 的外部上传。基线内核日志再次记录 `Received unknown response while uploading SDO 0x6040:00`，符合字典描述回复被上传状态机取走的表现。[IgH 官方开发邮件列表的既有问题报告](https://lists.etherlab.org/pipermail/etherlab-dev/attachments/20140531/7fd97097/attachment-0003.htm)也记录了这类重叠与响应错配。

`probe_connected.py` 现在临时开启主站 debug level 1，通过带微秒起始时间过滤的内核 journal 等待每个从站实际出现 `Fetched N SDOs and M entries`。`Fetching` 开始日志不算完成；全部完成后将调试级别降为 0，再进行外部 SDO。45 秒超时即退出并卸载，不猜测完成时间。

该等待也覆盖单台复位入口的前置诊断，但本轮没有再次执行复位。没有修改 IgH 内核源码；其他直接使用 IgH 的应用仍需处理自己的邮箱并发。现场结果只覆盖单台、上述时长，不能视为长期稳定性或周期实时性验收。

厂家 [Diamond 用户手册第 7.2 节](https://innodrive.ru/upload/iblock/08d/ktk23ukimoo3b3efav665ctg469cf02v.pdf)将主站类型 0 定义为标准 402 方式，当前这一项符合要求。

另找到厂家 [EtherCAT Application Manual，表 3-61 / PDF 第 50 页](https://innodrive.ru/upload/iblock/108/un3h57i90dw9eeavvbhwrdg9b0dt39qc.pdf#page=50)，该版列出的编码器类型只有 1–4，未覆盖实际读取的 5。它可能是其他固件扩展，也可能与电机不匹配；必须核对实物型号和对应固件说明，不能根据旧版手册擅自改成 3 或其他值。

该专用手册也确认 `6040` bit 7 上升沿对应故障复位。实际设备对象字典将 `6040:00` 声明为 PREOP/SAFEOP/OP 均可读写。这证明 PREOP 写对象受支持，但尚不能证明该固件在 PREOP 中执行完整内部故障恢复。仍需以驱动器实际状态变化或对应固件说明为依据。

## PDO 与 0x738A 的关系

已确认 `1C12/1C13` 的第二个 PDO 索引为零，导致 IgH 扫描 `0000:00` 失败，且默认布局与原 PMAC 工程不同。这会影响后续过程数据初始化与进入运行状态，仍需规范配置。

当前状态字和错误码都通过按索引的 SDO 直接读取，未使用应用 PDO 字节偏移。字典等待后这些读数稳定，所以不能将 `0x738A` 解释成“我们读错了 PDO 偏移”。厂家将该码定义为编码器通信 CRC 错误；编码器协议/参数、物理信号和内部故障锁存仍是待区分的原因。

后续先用实物驱动器、电机/编码器型号核对类型 5 与 17/16 位参数。再根据准确 ESI/固件要求建立禁止使能的周期通信、验证 PDO 和 DC，以判断复位是否需要运行中的周期处理。本轮没有进行这些写入或状态升级。
