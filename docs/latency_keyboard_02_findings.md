## 数据

## 已确认的耗时来源

| 所有事务的平均值 | PVT 提交 | 反馈快照 |
| --- | ---: | ---: |
| 事务总耗时 | 9.948 ms | 8.876 ms |
| Modbus 读调用累计 | 2.498 ms | 2.721 ms |
| Modbus 写调用累计 | 2.075 ms | 0.525 ms |
| 显式轮询休眠累计 | 5.324 ms | 5.595 ms |
| 其他及计时开销 | 0.051 ms | 0.035 ms |
| 休眠占事务累计耗时 | 53.5% | 63.0% |

以上是逐事务平均值，因此可以相加；不是把分项中位数或 P99 相加。Modbus 调用包括库、网络、控制器响应和操作系统调度，不是纯网络传输时间。

1,882 次 PVT 中 1,018 次休眠，384 次反馈中 201 次休眠；发生休眠的每次事务均只请求了一次 1 ms 休眠。只统计这些真正休眠的事务：

| 请求 1 ms | 实际中位数 | 实际 P95 | 实际最大值 |
| --- | ---: | ---: | ---: |
| PVT 轮询 | 10.103 ms | 11.592 ms | 14.622 ms |
| 反馈轮询 | 10.364 ms | 13.716 ms | 13.858 ms |

这次是实机事务内部直接计时，确认了短休眠被放大的现象，不再只是第一轮独立 sleep 探针的推断。实际值不固定为 15.6 ms，不应描述成“每次必等 15.6 ms”。即使改进休眠，也可能因为更早检查而增加轮询次数，不能把所有超出的休眠简单当成必然可节省时间。

周期末有 1,175 次正时长休眠；实际值减去请求值的额外延迟，中位数 8.754 ms，P95 13.269 ms，最大 15.782 ms。此项与协议轮询休眠独立记录，说明不能只改协议中的一个 sleep 而忽略 driver 周期末调度。

## 对控制的影响

实际平均循环为 43.725 Hz，平均周期约 22.87 ms，P95 周期间隔 32.099 ms。非 hold 时 IK+映射中位数 0.832 ms，P99 2.254 ms，最大 2.905 ms，仍不是主要占时环节。日志写入中位数 0.055 ms，最大 0.318 ms。

软件队列范围 1–11 点，中位数 6，未证明控制器内部插补缓冲或 run_state。按本地 20 ms 段消费逻辑，平均供点低于 50 段/秒的问题仍存在。WORLD X/Z 原始目标与滤波目标最大差距为 2.2/2.6 mm。没有记录控制器插补指令，所以仍不将主机目标减编码器反馈解释成伺服跟随误差。

本轮记录的提交均成功。没有新增控制器请求、重试或执行参数修改。图表 findings.png 将所有事务的平均耗时分解与真正休眠事务的请求/实耗对比并列；完整原始图和统计在 charts/ 下，findings.json 保存派生结果。

## 下一步

优先对上位机等待方式做可回退对照，覆盖协议轮询和 driver 周期末等待，保持当前 50 Hz、1 ms 轮询请求值、反馈频率、滤波/限速、token/ACK 语义和缓冲门槛。先离线验证短等待精度、CPU 使用和异常退出，再由用户安排同轨迹实机采集第三轮。不要直接改成无休眠忙轮询，也不要跳过 ACK。

验收看实际周期是否接近 20 ms、PVT/反馈耗时及队列变化是否改善，同时关注请求次数是否增加、是否出现队列溢出/断流与运动不平顺。若供点稳定而固定排队延迟仍明显，再单独评估缓冲门槛；若控制器指令及时而反馈仍滞后，再检查伺服与机械。现在不先调电机增益或修改 IK。
