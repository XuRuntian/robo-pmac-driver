PMAC 通信与生命周期修复（2026-09-08，协议 v2）

这次修改解决启动锁定旧反馈、PVT 半帧提交与无确认、退出遗留轨迹、回零状态地址/宽度错误和手动停止后无法设零。Python 驱动与 PMAC 工程必须配套更新；ZMQ/LeRobot 的应用协议仍为 v1，动作字段保持原定义。

**行为与启动顺序**

1. 建立 Modbus 连接，将复位完成寄存器清零，然后通过 SSH 请求一次 PLC 4 复位。
2. PLC 4 暂停 PLC 2/3，终止坐标运动，清空环形缓冲、请求和错误状态，恢复未完成回零的临时限流；完成后使能 PLC 2/3 并回传完成标记。PLC 1 的启用状态与机械参数保持原设置。
3. Python 等待完成标记，检查协议版本，再请求一份新的编码器/回零状态快照。PLC 2 采集、编码、确认后冻结这份快照，直到下一次请求。读取不到新快照、反馈失败或启动全零时停止启动。
4. Python 用该快照初始化位置目标和零速度，然后启动 prog 1，等待 PVT ready。`connect_and_home()` 的名字为兼容保留，实际作用是建立参考，不执行物理回零。`safe_boot_and_home()` 的两种旧参数选择现在统一使用上述 PLC 4 完成确认流程。

每个 PVT 段依次执行：等旧请求完成 → 写位置 → 写时长 → 写速度 → 最后写 token → 等 PLC 清请求并核对 accepted token。任何写入失败都不会继续提交；提交后的超时属于执行状态不确定，不自动重发。错误会锁定 Python 流并尝试终止坐标运动，必须完整重启恢复。PLC 检测缓冲满、无效帧、未就绪状态、运动程序停止时会返回错误并终止流。

accepted 只表示已进入控制器软件队列，不表示电机已经到达。上位机回参考点时继续发送零速度尾段，并按配置容差检查新反馈，不再用参考值冒充无效反馈。`--return-check-tolerance-pulses 0` 仍表示关闭位置容差判断；尾段至少持续 0.5 s，启用容差检查时最多等待 3 s。直线轴回参考轨迹如果会超过 PLC 步长限制，会在发送前要求增大 `--return-duration`。

正常关闭、Ctrl+C、服务 SIGTERM 和受管理的异常退出会发送坐标 abort，并清空软件队列、请求位。正常关闭不以重新使能电机作为停止手段。PLC 2 在收到第一帧后监控 PVT 数据到达时间，断流超过 0.5 s 会终止流并锁定故障；这也覆盖 Python 被强制终止、无法运行 finally 的情况。实际停止时间还包括控制器和驱动器的减速响应。

服务端 hold/命令超时会冻结最后提交的五轴位置，后续发零速度保持段，停止继续迭代 IK。已进入 PMAC 插补队列的点需要执行或被 abort，因此 hold 不是硬件急停。进程退出或 PVT 故障才走 abort/清队列。

token 在 1–255 间轮换，下一次从最后确认值生成，避免重复提交与多字节触发值的部分更新。锁串行化同一 Python 客户端中的快照、PVT 和回零访问。本协议要求一个驱动进程独占邮箱，不支持多个进程同时直连控制器提交命令。

位置反馈不再是随意读取就会更新的连续寄存器。业务代码使用 `robot.read_positions()` 请求新快照，回零状态使用 `homer.read_status()`。直接读地址 10/18 得到的只是上次确认的快照。仓库中相关旧读取入口已经改用该方法。

**回零状态与退出**

| 状态 | 含义 | 允许的后续行为 |
|---|---|---|
| 0 | 空闲 | 命令 1 启动 |
| 1 | 使能/限流后的等待 | 进入 jog；命令 2 停止、4 取消 |
| 2 | 正在 jog | 命令 2 停止、4 取消或保护停止 |
| 3 | 已停止，等待确认 | 命令 3 设零、4 取消 |
| 4 | 已发 hmz，等待反馈证实 | 成功进入 0 并置 done；失败返回 3 |

命令 2 保留状态 3，因此人工停止后命令 3 可以执行。命令 4 退出且不设零。所有停止、取消、保护和复位路径恢复原 MaxDac；新的临时限流不会增大本来更低的 MaxDac。状态、原因、电流、跟随误差全部通过同一 int32 编码，不再混用 byte 与 register 地址或 16/32 位宽度。

回零进入前先终止 PVT，避免坐标运动与轴 5 jog 同时争用电机。回零中超过 1 s 没有新的反馈快照请求，会停止并回传原因 8。设零发出后，PLC 需要看到轴 5 位置在一个计数以内才置 done，Python 同时检查反馈整数为零；2 s 内未确认则回传原因 10。人工示例在反馈异常和退出时执行取消，只有设零验证通过才打印成功。

PVT 故障码：1=缓冲满，2=未就绪或与回零冲突，3=断流超时，4=运动程序停止，5=无效时长/token。回零保留原原因 2（跟随误差）与 9（人工停止/取消），新增 8（反馈断流）、10（设零未确认）。

**这次还处理的服务问题**

- 程序从初始化阶段就登记资源清理，参考检查失败、端口绑定失败等也会关闭已启动的机器人。
- 服务读取 PLC 的 Axis5_MaxStep，取它和用户速度限制的较小值。未提高现有 PLC 的步长和速度参数。
- 限幅后的已提交脉冲反算为下一轮 IK 初值，减少软件预测状态与实际命令的偏离。新增 `commanded_tip_error_m` 表示限幅后命令对应的 FK 误差；原 `ik_error_m` 仍表示求解器误差，两者都不是实测末端误差。
- 未实现接收端的旧 `move_joints()` 点位协议改为明确报错，避免无响应却显示已发送。没有把带 accel/scurve 参数的旧接口悄悄变成另一种轨迹语义。
- 硬件版和两个主要仿真 IK 均加入边界内向差分：插入到 255 mm 后可以回退到 254 mm，固定插入约束仍然保持固定。
- Modbus/SSH 错误向调用方传播；int32 溢出、非有限数、错误轴数和不合法时长在发送前拒绝。

**配套更新与验证边界**

本地代码已修改，未连接、下载或运行 PMAC。上机时需在 Power PMAC IDE 重新构建并下载本次修改的全局定义、ModbusCodec/SystemInit 库、PLC 2/3/4 和 prog 1，再启动新 Python 驱动。IDE 生成的符号表与 C 头文件由构建更新，不手工修改。协议不一致会拒绝启动；旧 Python 与新 PLC 也不兼容连续提交。

默认 `capture_current` 仍要求启动时编码器参考对应已知机器人形状。这次没有改变机械标定。原 PLC 1 的 ±600000/±610000 恢复目标问题按本次约定留待硬件调试；255 mm 的 IK 范围与真实直线行程、Motor[5].MaxSpeed、加减速参数，以及 10 点预缓冲的延迟，也仍需结合硬件统一和测量。PVT 主程序的插补和轴 5 钳位公式本次保留。

当前 60 项离线测试全部通过，覆盖 Python 客户端的错误注入、回零协议交互、生命周期、限幅后的状态同步和真实 ZMQ dry-run 进程。另使用 Pixi 调用现有环境，分别验证仿真重构版和线程版的 position/pos_z 上限回退，两者与硬件版均成功回到 254 mm。未把这些测试当作 PLC 编译或物理轨迹测试。运行命令：
