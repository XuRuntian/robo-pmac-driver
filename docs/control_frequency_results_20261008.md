# 2026-10-08 离线频率摸底记录

## 结论范围

已实现并运行离线验证工具。现有代码在平滑、可达、warm-start 条件下的 IK 计算远快于 50 Hz；但困难目标和周期调度带来不同上限，不能给整个系统一个无条件的“最高频率”。目前没有证据要求把 IK 迁移到 PMAC，也没有证据证明实机滞后由 IK 造成。

所有数据均为本机离线合成输入，未连接硬件、读取编码器、执行运动、修改生产参数。计算链路仅覆盖文档列出的子集，不包括通信、PLC 队列和伺服。压力场景的精度失败不能等同电机跟随失败。

环境：Intel Core Ultra 5 225H，14 个逻辑处理器；Windows build 26200；Python 3.10.20；NumPy 2.2.6。基线提交 712078d，新增 benchmark 文件未提交。后台负载未受控，未改变系统定时器、进程优先级或电源设置，不是硬实时认证。首次运行安装绘图库发生在测量之前。

## 无等待计算筛查

| 负载 | 频率 | P99 计算耗时 ms | 观测最大 ms | 计算超期率 |
| --- | ---: | ---: | ---: | ---: |
| IK 正常可达 | 500 | 0.772 | 1.298 | 0% |
| IK 近直线可达 | 500 | 0.823 | 1.152 | 0% |
| IK 边界内可达 | 500 | 0.851 | 1.430 | 0% |
| pipeline 正常 | 300 | 0.988 | 1.770 | 0% |
| pipeline 近直线 | 300 | 1.179 | 2.402 | 0% |
| pipeline 正常 | 500 | 1.156 | 2.362 | 0.08% |
| pipeline 近直线 | 500 | 1.022 | 5.030 | 0.04% |
| pipeline 边界压力 | 100 | 6.680 | 9.955 | 0% |
| pipeline 边界压力 | 150 | 6.746 | 10.776 | 1.47% |
| IK 不可达压力 | 100 | 7.489 | 8.943 | 0% |
| IK 不可达压力 | 150 | 7.478 | 9.016 | 7.07% |

追加纯 IK 高频试验：750 Hz 时正常场景超期 0.03%、近直线 0%、边界内 0.21%；1000 Hz 三组均出现超期（0.14%–0.24%）；1500 Hz 三组均出现超期（2.23%–2.85%）。因此三个可达场景共同通过的最高已测档位是 500 Hz，500–750 Hz 之间尚未细分。不能称“Python IK 极限恰好是 500 Hz”。

上述可达 IK 场景以及正常/近直线 pipeline 的求解器收敛率均为 100%。例如 300 Hz pipeline 正常场景最大模型位置误差约 0.00449 mm，近直线约 0.00400 mm。该精度来自同一模型的 FK/IK 一致性，并非机器人实测精度。

边界 WORLD 压力轨迹约 47% 的帧收敛，大 WORLD 压力轨迹约 26% 收敛；它们不是可达性受保证的任务，耗时结果只能作为压力数据，不是正常轨迹精度验收。FK 生成的边界内可达轨迹则保持收敛，二者不能混为一谈。

| 场景 | 频率 Hz | P99 计算 ms | 计算超期率 | 完成截止时间超期率 |
| --- | ---: | ---: | ---: | ---: |
| 正常 | 100 | 2.653 | 0% | 35.90% |
| 正常 | 125 | 1.901 | 0% | 48.00% |
| 正常 | 150 | 2.865 | 0.13% | 57.20% |
| 正常 | 300 | 1.418 | 0.03% | 78.50% |
| 正常 | 500 | 2.382 | 2.26% | 88.02% |
| 近直线 | 100 | 2.632 | 0% | 36.10% |
| 边界压力 | 100 | 8.454 | 0% | 46.90% |
| 大 WORLD 压力 | 100 | 7.774 | 0.10% | 53.00% |

计算超期只判断本帧工作耗时是否超过周期；完成截止时间还包括唤醒延迟和之前积累的落后，两者不能相互替代。例如正常 100 Hz 计算无超期，但固定截止时间有 35.9% 超期，最大完成迟到约 14.22 ms。此现象提示需要单独验证运行环境的周期调度，不能据此认为 IK 每帧要算十几毫秒。

paced 使用普通 sleep 和固定时间轴，当前 driver 超期会重置下一周期时间；这不是对现有 driver 的完整运行测量。没有调整定时器，也未测试部署环境是否相同，因此不把它直接归因于某个 Windows 定时器机制。当前 paced 数据没有任何已测频率实现所有场景零截止时间超期，不能从本轮给出“稳定端到端最高控制频率”。

## 后续顺序

1. 明确部署时实际 Python 解释器与本次是否一致；以 driver 的周期策略补测实际间隔、调度延迟，先解释 paced 现象。保留计算计时与调度计时的区分。
2. 对候选频率做更长时间重复确认和分界细化，记录后台负载。不要仅根据本次无等待结果把实机改为 300/500 Hz。
3. 再在当前 50 Hz 下取证通信耗时、排队深度、控制器插补指令和同期编码器反馈，定位电机滞后。本地 PVT 有 >5 ms 段时长限制，200 Hz 及以上与当前一周期一段方式不兼容。
